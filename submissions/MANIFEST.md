## 必须记住的评测经验（踩过的坑）

1. **回放里的 action 数组相对 observation 整体错位 +1。**
   `steps[t].observation` 是第 t 步的**前**状态；产生它的动作在 `steps[t+1].action`。
   拿 `steps[t].action` 直接喂会得到完全错误的复原。修正后 12/12 局可比特级复现。
   **任何从回放复原 agent 的代码都必须用 `ACTION_SHIFT = 1`。**

2. **反事实评测用「冻结对手轨迹」，会系统性高估我们。**
   对手在反事实里只是重放录像，不会针对我们应变，所以显得比线上弱。
   后果：本地判「更强」的方案（如路线库 29.2% vs 25.0%）一到线上就翻车。
   → **本地结论只能当方向参考，不能当验收依据。**

3. **线上天梯的前 30 分钟爬升速度是很好用的快筛。**
   实测：好版本半小时到 1300；差版本半小时只有 1000。
   比等 6–8 小时收敛快得多。（`kaggle competitions submissions kaggriculture`）

4. **固定单表 > 任何运行时选表机制。** 三组实测：

   | 方案 | 结构 | 线上分 |
   |---|---|---|
   | Subramanya N 单表 + 修复层 | **固定单表** | **1776.7** ★ |
   | 11 张表路线库 | 按商店前缀选表 | 1181.8 |
   | V38 | 5 张表按商店模式选 | 1152.7 |

   两个「选表」方案几乎同分，都远低于固定单表 —— 所以问题出在**选表机制本身**，不是表的质量。
   推测原因：165 种商店前缀里库里只有 11 种，匹配不上时选表退化成「取列表第一张」，
   比那张精选过的表更差。

5. **搞清楚「赢的那一版到底是什么」—— 用 100% 精确匹配反查来源。**
   2026-09-16 才发现：历史文件 `candidates/T_adarsh_repair.py`（拿 1776.7 的那份）
   **根本不是 ADARSH 的表**，而是 `ep108075223 座位1 = Subramanya N` 的表 **100.0% 精确复制**。
   文件名叫 adarsh，只是因为建表时误以为 ADARSH 在那个座位（ADARSH 实际坐在座位 0）。
   反查方法：把候选的 `_TABLE_OVERRIDE` 与每局每个座位的表**逐回合精确比对**：
   - 相似度 100% → 就是来源；
   - ADARSH 族内部彼此 30%–96%；
   - 跨族（如 mikelou1 vs ADARSH）只有 4%。
   **命名不可信，指纹才可信。** 选候选表时要按「与已验证赢家的风格相似度」挑，不要按名字挑。

6. **mikelou1（队伍 55341437，峰值 3051）这条路已死。**
   它 119 局、105 个不同对手的动作序列 **97%–99% 完全相同** —— 是一张彻底固定的计划。
   移植到九月对局只有 **0胜24负、份额 34.9%**（55,396 / 103,463）。
   提取本身无误（3/3 局比特级复现，含 147,308 那局）。
   原因：农场动作固定 → 产出固定；**卖单时机也固定** → 收入完全取决于对手是否砸价。
   在它自己的分数段里没人砸价，换个环境就崩。所以「固定单表」的天花板不由农场计划好坏决定，
   而由卖单时机是否撞上对手的市场决定。

7. **每天只能交 5 份**（规则 2.SUBMISSION LIMITS：「You may submit a maximum of five (5)
   Submissions per day」）。超额时 CLI 报的是 `400 Client Error: Bad Request ... CreateSubmission`，
   看着像包有问题，其实是配额。**批量提交前先数一下当天已交几份**（`kaggle competitions
   submissions kaggriculture`，注意按 UTC 日期算）。
   只有**提交过的版本**才有分数；`_docx/` 下的本地反事实评测一律不算数。

8. **线上爬升要等，不要提前下结论。** 实测同一份提交：半小时 1181.8 → 一个多小时 1321.1，仍在涨。
   判断一份候选至少要等到 1 小时以上，且必须和同期基准比（赢家那版半小时到 1300）。

9. **⚠️ 严重更正（2026-09-16 19:26）：一条「换表轴已证伪」的结论是错的，因为下早了。**

   错误原因：**拿不同局数的提交直接比分数。** 实测：

   | ref | 表来源 | 已跑局数 | 线上分 |
   |---|---|---|---|
   | 56268283 | Subramanya N | **85** | 1767.3 |
   | 56275283 | 路线库（11 张表 + 选表） | **20** | 1321.1 |
   | 56276676 | Michael Shihong Zhang | **10** | 1309.8 |
   | 56276674 | tllswelp | **11** | 1127.0 |
   | 56276673 | Zhongyi Dai | **1** | 600.0（起始分，**还没跑**） |

   新提交都是 600 起步、随局数爬升。**10 局的 1309.8 和 85 局的 1767.3 不可比。**
   56276673 只有 1 局，那个 600.0 根本不是失败。

   → **铁律：比分数必须先比局数。**
   `kaggle competitions episodes <ref> -v | Measure-Object -Line`
   任何「新方案更差」的判断，都必须等到局数可比再下。此前所有基于单次短时读数的
   「证伪」结论一律作废（包括策略库那条）。

   话虽如此，**「换表轴」目前仍只是「未判定」，不是「已验证」** —— 需要等它们跑到
   与赢家可比的局数（80+）再看谁高谁低。

10. **真正的瓶颈在「卖出」这一层，已被两条独立证据锁定：**
    - mikelou1 的农场动作固定（97–99% 一致）、产出因此固定，但换环境后收入从 ~86k 掉到 55k
      —— 差异只能来自价格；
    - 价格表里**高价作物（草莓/甜瓜/牛奶/羊毛）的 `above_target` 是 1.6–3.6**，只要超卖一点，
      价格直接砸到 $1 地板。
    固定卖单时序必然超卖。而**所有试过的方案（V38、路线库、全部换表）共用同一套固定卖单**，
    所以分数都卡在同一档 —— 这可能才是 15 次只有 1 次成功的根本原因。
    → 下一步若要继续，唯一有依据的方向是**把卖单从「录死的时序」换成「按实时价格算」**，
    而不是继续换表。

## 远程仓库

`origin` = https://github.com/linjunren1016/Kaggriculture

**本机网络阻断 `github.com:443`**（TCP 直连超时），但 `api.github.com` / `codeload.github.com` 可达。
所以 push 必须走代理。已在本仓库配好 **repo-local** 代理（不动全局 git 配置）：

```bash
git -C <repo> config http.proxy            # -> http://127.0.0.1:7897
```

**推之前先确认代理软件是开着的**（Clash 默认端口 7897）。代理关着时 `git push` 会报
`Failed to connect to github.com port 443 via 127.0.0.1`，那不是仓库问题，开代理即可。

日常提交：

```bash
git add -A && git commit -m "submit: <ref> <机制> <分数>"
git push
```
